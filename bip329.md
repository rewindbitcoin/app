# BIP-329 Labels Reference

This app uses standard BIP-329 labels as wallet metadata. Labels are private
data and must stay in encrypted per-wallet storage. Import/export must remain an
explicit user action.

Keep this file up to date whenever auto-labels are added, changed, or removed.

## Core Rule

Use only standard BIP-329 label targets for now:

- `tx`
- `addr`
- `pubkey`
- `input`
- `output`
- `xpub`

Do not add a custom `vault` label type. BIP-329 has no vault entity.

## Vault Names

Vault display names should be stored as the label of the vault locked output:

- `output:<vault txid>:<vault vout>` = vault name fragment

Store only the name fragment, not the localized noun. For example, store `1` or
`Secure`, not `Vault 1` or `Vault Secure`. UI copy decides whether to render
`Vault {{vaultName}}`, `Unfreeze: Vault {{vaultName}}`, etc.

Vault name editing should edit this fragment in-place from the vault card. If
the user clears the custom name, remove the BIP-329 label and fall back to the
generated numeric name.

The internal `vaultId` remains authoritative and must not be replaced by a
label. Labels are mutable, importable, and removable.

If no vault output label exists, fall back to the generated vault name fragment,
such as `1`.

## Import Conflicts

Import is conservative:

- Missing existing fields may be filled by import.
- Omitted imported fields do not clear existing fields.
- If an imported record disagrees with an existing `label`, `origin`, or
  `spendable`, skip the whole record and report a conflict.
- Existing data wins.

## Manual Labels

Receive:

- User label goes to `addr:<receiveAddress>`.

Send:

- User label goes to `tx:<sent txid>`.

Create Vault:

- User vault name fragment goes to `output:<vault txid>:<vault vout>`.

## Auto Labels

Auto labels should be set only when empty. Never overwrite a user/imported label
without an explicit user action.

Currently implemented auto-labels:

| Flow | BIP-329 type | Ref | Label |
| --- | --- | --- | --- |
| Create Vault | `tx` | `<vaultTxId>` | `Vault activation: <vault name>` |
| Create Vault | `tx` | `<backupTxId>` | `On-chain backup: <vault name>` |
| Create Vault | `addr` | `<emergencyAddress>` | `Emergency address: <vault name>` |
| Create Vault | `output` | `<vaultTxId>:<vaultOutputVout>` | `<vault name>` |
| Create Vault | `output` | `<vaultTxId>:<triggerReserveVout>` | `Unfreeze fee reserve: <vault name>` |
| Create Vault | `output` | `<vaultTxId>:<changeVout>` | `Vault change: <vault name>` |
| Unfreeze / Trigger | `tx` | `<triggerTxId>` | `Unfreeze: <vault name>` |
| Unfreeze / Trigger | `output` | `<triggerTxId>:<triggerOutputVout>` | `Unfreeze output: <vault name>` |
| Unfreeze / Trigger with CPFP | `tx` | `<triggerCpfpTxId>` | `Unfreeze fee boost: <vault name>` |
| Unfreeze / Trigger with CPFP | `output` | `<triggerCpfpTxId>:<changeVout>` | `Unfreeze fee boost change: <vault name>` |
| Rescue | `tx` | `<rescueTxId>` | `Rescue: <vault name>` |
| Rescue with CPFP | `tx` | `<rescueCpfpTxId>` | `Rescue fee boost: <vault name>` |
| Faucet | `addr` | `<faucetReceiveAddress>` | `Test coins` |

Replacement transactions use the same durable labels as first attempts:

- Replacement trigger transaction: `Unfreeze: <vault name>`
- Replacement rescue transaction: `Rescue: <vault name>`
- Replacement unfreeze CPFP child: `Unfreeze fee boost: <vault name>`
- Replacement rescue CPFP child: `Rescue fee boost: <vault name>`

Use "accelerate" in button/modal copy only. Persistent BIP-329 labels should
describe the durable transaction intent, not the temporary action the user took
to replace or bump a transaction.

## Reserve Change Outputs

Normal-wallet reserve change outputs are important and should be labeled.

Trigger reserve change goes back to normal wallet change and should still be
identified as related to that vault's unfreeze fee reserve lineage.

Rescue reserve change goes back to the temporary rescue wallet's change branch
and should not be stored in the active wallet's labels.

## Avoid Noisy Labels

Do not label every output by default.

Prefer labels for user-meaningful outputs and transactions:

- vault locked outputs
- reserve funding outputs
- normal-wallet reserve change outputs
- user send transactions
- user receive addresses

Avoid auto-labeling purely technical outputs unless they can later appear as
wallet UTXOs or user-visible history entries.

## Emergency Addresses

Do not label the emergency address itself per vault by default. Multiple vaults
may intentionally share one emergency address, so a per-vault `addr` label would
conflict. Label rescue destination outputs instead.
